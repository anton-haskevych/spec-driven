# Phase 4 preflight — 4.2a–4.5 (2026-10-12)

Plan: `phases/phase-4-crew-tools.md` (re-planned) + technical.md → *Phase 4*. Recon:
`2026-10-12-4.1-recon.md`. House rules: `skills/spec/principles.md`.

## Findings that change the plan

1. **Babysitter titles don't parse.** `parseLaunchTitle` (`T/launch/title.ts:16-21`) accepts a third
   word only if `isPhaseId`, so `checkout babysit B` reads `undefined`. Tick must tell workers from
   babysitters by title, and the board's `launchedSpec` (`T/board/attribution.ts:32-35`) and
   `focusSession` (`T/board/focus.ts:146`) silently miss babysitters today. Fix in `title.ts`
   (a `group` field for babysit), own commit.
2. **`crew launch` would copy `launchCommand`'s place-and-launch body** (`T/commands/launch.ts:34-42`).
   Second use is concrete: extract the placement-to-launch step into `T/launch/` and have both call
   it. `launchInBackground` (`T/launch/background.ts:12-19`) returns only a string, so the id the
   crew must record is re-parsed from text; return `Result<BackgroundSession>` and render the line in
   the command (`launch-background.test.ts` asserts the string: keep the rendered line identical).
3. **One load gives tick everything.** `loadBoardInputs` (`T/board/load.ts:42-75`, non-local) already
   holds mainline `states` (phase `code`), `nodes` (`meta.ship` for the brief), held `claims` with
   status, live `sessions` (overseer check) and the worktree list; `buildBoard` (`T/board/lanes.ts:38`)
   turns it into the ready lane. Tick loads it once, never `loadBoard` + `heldClaims` +
   `loadLiveSessions` separately.
4. **Claims carry stale session ids** (`gotcha-session-id-can-change-mid-session`): match a launched
   session to its claim by key (`<spec>#<phase>`, `<spec>#pr-<group>`), never by `sessionId`.
5. **A just-launched worker hasn't claimed yet**, so its phase still reads ready on the board for a
   while. The one-worker-per-spec pick rule is what stops a double launch: pin it with a test.
