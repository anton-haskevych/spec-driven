## Findings that change the plan

1. **`record sync` replays nothing today.** `commands/record.ts:29-31` builds `runners: {}` and
   `validate: () => []`, so the deliverable "one `record sync` lands both" can't pass by adding a runner in
   the tick path alone. The tick runner and `validateRecordDoc` must be registered in `systemRecordDeps`, and
   the runner needs a `Git` (it pushes), so the deps take a runner factory over `git`.
2. **A runner can't say "offline".** `record/outbox.ts:21` types a runner as `(args) => RecordPlan`; the flush
   of a queued tick must push its commit first, and an unreachable origin there must leave the entry queued,
   not mark it refused (a plan can only refuse). Widen the runner's return to `RecordPlan | { offline }`, and
   keep the pure plan separate from the pushing runner so reads can replay the plan without a push.
3. **No read overlay exists.** "The pack shows both done and the pending count" needs reads to lay queued
   intents over the view; `plan/read-plans.ts:18-21` has no outbox step and `context/board-lines.ts:10` no
   pending count. It is part of this chunk, not phase 3b.
4. **The refusal names who and when, which the record doesn't hold.** `plan/docs/phase-doc.ts:7-15` `Task`
   has `evidence` only; `tick: refused … closed 4 min ago by the session in tree pr-a` and "already done when
   this session did it" need the closing session, tree and time on the task.
5. **`pushBranch` can't tell rejected from offline**: `publish/push.ts:35` runs `push -q` and returns the
   stderr reason. Use `--porcelain` and `core/remote-push.ts:19` `pushOutcome`'s rule (`!` = rejected, no
   line = offline).

## Amendments

1. Commit order: dispatcher split → typed `pushBranch` → `Task` close fields + `plan/ops/tick.ts` → port +
   record tick + runners in `record sync` → overlay + pending line → two-clone and offline suites.
2. `Task` gains `doneAt`, `doneBy` (session id) and `doneIn` (tree folder name), all optional.
3. The record tick addresses tasks by id only; `#N` or a text prefix on a joined spec is refused with the open
   tasks and their ids. `phases/locate.ts` is unchanged (file specs only).
4. An offline push queues the intent directly (`queueIntent`), not through `sendIntent`: a second push attempt
   would wait out another timeout.

## Defaults applied

- Task phases and `Gate:` tasks don't push: their evidence is the given link/approval.
- `--evidence` on a code task is kept after the commit: `<sha> on origin/<branch> · <text>`.
- The read overlay lays every queued intent of this clone over the view, not only this session's: a sibling
  session on the same machine shouldn't be offered the phase either.
- A push failure we can't classify (auth with no prompt) reads as offline and queues.
